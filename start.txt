## Qué es Armonic (un párrafo)
Cada deploy de Armonic es una única instancia self-hosted que representa un solo server/comunidad — no es una plataforma multi-tenant. Una instancia arranca sin dueño; la primera persona que entra la contraseña compartida de la instancia la reclama y se vuelve admin; cualquier otro miembro entra vía un link de invitación de un solo uso que el admin genera (no hay registro público). El chat de texto y los canales de voz son por instancia; la voz es audio WebRTC relayado por el backend (tipo SFU).

## Qué debe hacer la app
Diseñá la app alrededor de **múltiples instancias de Armonic**, al estilo de un cliente Matrix/Element con varios homeservers — el usuario debe poder agregar varios backends de Armonic distintos (URLs de host distintas, ej. la instancia self-hosted de un amigo y una comunitaria) y cambiar entre ellas desde una pantalla principal, cada una mostrada como su propio "server". Esto es intencional aunque técnicamente un solo backend casi siempre expone un único server a un usuario dado — la multiplicidad que la app debe soportar es "conectarse a N instancias", no "N guilds dentro de una instancia" (el modelo de datos del backend técnicamente permite que un usuario pertenezca a más de un server ID dentro de una misma instancia, vía `get-servers` — manejá esa lista de forma genérica igual, pero es el caso secundario, no el foco).

### Pantallas / flujos necesarios
1. **Agregar servidor / home**: lista de instancias ya conectadas (cada una guarda su propia base URL + JWT), mostrando nombre/descripción/cantidad de miembros desde `GET {baseUrl}/info`. Una acción "+" para agregar una instancia nueva por URL.
2. **Onboarding de instancia**, bifurcando según el campo `claimed` de `GET {baseUrl}/info`:
   - `claimed: false` → **Flujo de claim**: pantalla de contraseña → `POST /claim/password {password}` → si funciona, pantalla de registro (usuario/contraseña) → `POST /claim/register {ticket, username, password}` → guardar el JWT devuelto, queda como admin. El ticket expira a los ~10 min — si `/claim/register` da 401, volver a la pantalla de contraseña.
   - `claimed: true` → **Pantalla de login**: `POST /auth/login {username, password}` → guardar JWT. (No existe endpoint de signup público — no construyas una pantalla de "registrarse" genérica.)
3. **Redención de invitación**: un link tipo `{baseUrl}?invite=<token>` debe abrir una pantalla de alta para una cuenta nueva: `GET /invite/status?token=` para mostrar a qué instancia pertenece y su vencimiento antes de confirmar, después `POST /invite/signup {token, username, password}` → guardar JWT. El mismo token no se puede usar dos veces (410 Gone en el segundo intento) — mostralo como "esta invitación ya no es válida", no como un error genérico.
4. **Vista de servidor** (una vez conectado+autenticado a una instancia): abrí el WebSocket en `ws(s)://{baseUrl}/ws` (esquema derivado de si la baseUrl es http o https), y como *primer mensaje* mandá `{"type":"auth","token":"<jwt>","name":"<display name opcional>"}`. Esperá `{"type":"auth-ok",...}` antes de mandar cualquier otra cosa — si mandás otro tipo de mensaje antes, el server cierra la conexión. Ante `{"type":"error","message":"unauthorized"}` como respuesta a auth podés reintentar auth en el mismo socket; pero mandar un mensaje que no sea auth mientras no estás autenticado hace que el server cierre la conexión.
   - Mandá `{"type":"get-servers"}` → recibís `{"type":"servers","servers":[{"id","name"}]}` (normalmente longitud 1). Si hay más de uno, dejá elegir al usuario.
   - Para el server elegido, mandá `{"type":"get-channels","serverId":"..."}` → recibís `{"type":"channels","serverId","channels":[{"id","serverId","name","type":"text"|"voice"}]}`.
   - Canal de texto: mandá `{"type":"get-messages","serverId","channelId"}` → recibís `{"type":"messages","messages":[{"id","channelId","serverId","userId","content","createdAt"},...]}`, más reciente primero — **hay que invertir el orden** para una vista de chat normal; no hay paginación, solo los últimos 50. Los mensajes nuevos llegan empujados como `{"type":"text-message","id","serverId","channelId","userId","content","createdAt"}` — **el que envía no recibe eco de su propio mensaje**, así que agregá los mensajes enviados a la UI local de forma optimista. Estos broadcasts no filtran por canal del lado del servidor — vas a recibir eventos `text-message` de todos los canales del server, filtrá por `channelId` del lado del cliente y cacheá el resto para cuando el usuario cambie de canal.
   - Enviar texto: `{"type":"text-message","serverId","channelId","content":"..."}`.
5. **Canal de voz** (WebRTC, usá `flutter_webrtc`): mandá `{"type":"join-voice","serverId","channelId"}`. **El backend inicia el offer, no el cliente** — vas a recibir `{"type":"offer","sdp":{...}}` justo después de unirte; creá un `RTCPeerConnection`, `setRemoteDescription(offer)`, `createAnswer()`, `setLocalDescription(answer)`, y mandá `{"type":"answer","sdp":{...}}` de vuelta. Agregá el track de audio local antes de responder (`getUserMedia({audio:true})`) para que el SDP de la respuesta lo refleje. Intercambiá candidatos ICE en ambas direcciones como `{"type":"candidate","candidate":{...}}` (mandá los tuyos a medida que se descubren vía `onIceCandidate`; aplicá los que llegan vía `addCandidate`). **Importante**: como el backend es un SFU que renegocia por participante, esperá `{"type":"offer",...}` adicionales sin pedirlos más adelante (ej. cuando otra persona se une/sale del canal) sobre la *misma* conexión — manejá `offer` como un evento repetible durante toda la sesión de voz, no como algo que pasa una sola vez tras `join-voice`, y respondé siempre con un `answer` nuevo.
6. **Moderación (opcional/secundario, solo si sobra tiempo)**: `create-invite` (`{"type":"create-invite","serverId"}` → `{"type":"invite-created","inviteToken","url"}`, solo dueño), `kick-voice`/`kick-server` (solo dueño, `{"type":"kick-voice","serverId","channelId","targetUserId"}` / `{"type":"kick-server","serverId","targetUserId"}`). El ack de `kick-server` (`{"type":"user-kicked","targetUserId"}`) solo se lo manda al admin que lo pidió — el usuario expulsado no recibe notificación en tiempo real por el backend actual, no construyas una UI que asuma que sí.

## Auth/almacenamiento
- Los JWT expiran a los 7 días; guardalos por instancia (base URL → token) en almacenamiento seguro (`flutter_secure_storage`), no compartido entre instancias.
- Fuera de `/info`, `/claim/password`, `/claim/register`, `/invite/status`, `/invite/signup`, el único otro endpoint HTTP es `/auth/login` — no existe `/auth/signup`. No construyas una pantalla genérica de "registrarse"; una cuenta solo se crea vía el flujo de claim (primer admin) o un link de invitación.
- El CORS del backend está completamente abierto (para dev, no hardened) — no es un problema del cliente, no te sorprendas si todo funciona cross-origin en Flutter web sin configuración extra.

## Paquetes sugeridos
- `http` o `dio` para las llamadas REST.
- `web_socket_channel` para la conexión WS (funciona en mobile/web/desktop).
- `flutter_webrtc` para el canal de voz (compatible con la implementación `pion/webrtc` del backend — SDP/ICE estándar, sin framing custom).
- `flutter_secure_storage` para el JWT por instancia.
- Manejo de estado: a tu criterio (`provider` o `riverpod`), no es el foco de esta tarea.
